# Limitations

Read this before trusting any output.

## Fundamental

- **No proof of anything.** The tool renders candidates and runs only
  static/structural checks. It never invokes a formal or simulation engine, so
  it cannot and does not establish that a property holds.
- **Candidates only.** Every emitted property has `status =
  candidate_rendered_offline`. "Rendered" and "compiled" are not "verified".

## Decomposition / classification

- Clause splitting is on explicit punctuation/connective boundaries only
  (`; . , and while`). Requirements phrased without those boundaries stay as a
  single clause; over-punctuated requirements may split into sibling clauses
  that ground to the same property (deduplicated, but the split is still coarse).
- Classification is a **transparent keyword heuristic**, not NLU. It can
  mis-file a cleverly worded clause. Rationale is emitted and any ambiguous case
  is flagged, but a human must confirm every classification.

## Grounding

- A term is resolved only by an exact Manifest match or a clearly-labelled,
  low-confidence alias (suffix / underscore-component match). Real designs with
  many similarly-named signals may need author `signals:` hints and manual
  disambiguation. Multiple exact matches across modules are flagged, not
  auto-resolved.
- Prose identifier extraction uses a small stopword list. It can miss a signal
  named like an English word (it becomes unresolved — safe) or surface a
  non-signal token (it stays unresolved unless the Manifest happens to contain
  it).

## Candidate SVA

- **Active-low reset caveat.** The renderer emits `disable iff (<reset>)` using
  the Manifest's reset candidate verbatim. If that reset is active-low (e.g.
  `rst_n`), the correct clause is `disable iff (!rst_n)`. The tool does **not**
  reliably know reset polarity, so a reviewer must fix the polarity. This is a
  known, documented gap.
- The per-category templates are a small fixed set of shapes. They encode a
  *plausible* reading of the requirement, not the only reading. For example
  access control is rendered as `action |-> grant`; whether the true intent is
  same-cycle, next-cycle, or "granted at request time" is a review decision.
- Bounded-response windows default to `##[1:3]`. The real timing bound must come
  from the requirement and be set by a human.
- Signal *selection* within a category is keyword-driven (`grant`, `priv`,
  `lock`, `fault`, ...). If your naming differs, the wrong pair may be chosen or
  emission may be skipped. Skips are always recorded, never silent.

## Information-flow-adjacent checks

- These are **structural equality comparisons only** (`!(sink == secret)`).
  They are NOT non-interference / taint / hyperproperty proofs and will miss
  timing channels, partial leakage, and functional-dependence leaks. Treat them
  as a coarse smoke check.

## Mutations

- Mutations are should-fail witnesses generated by textual transformation of the
  candidate SVA. They are heuristic sanity aids: a mutation that does *not* fail
  under a tool is a signal the original property may be vacuous, but a mutation
  that *does* fail proves nothing about the original's correctness.

## Roadmap (explicitly deferred)

- Reset-polarity-aware `disable iff` (needs polarity from Manifest heuristics).
- Richer temporal forms (`throughout`, `s_until`, multi-cycle sequences).
- An optional adapter to hand candidates to a real formal tool and ingest its
  PASS/FAIL/UNKNOWN evidence (kept out of scope per the v0.1 spec).
- LLM-assisted clause classification behind the deterministic validators.
